### 1.4 功能缺口（本方案要补齐的）

| 缺口 | 现状 | 影响 |
|---|---|---|
| **底部 Tab 导航** | ServerConfigScreen → ChatScreen 顺序切换；Settings 是全屏覆盖层（`showSettings` 状态） | 无 Files 入口；多页面无统一导航骨架 |
| **SSE 断线重连** | `ReasonixSseClient.onFailure` 直接 `close()`，无重连 | 网络抖动即断流，必须重进应用 |
| **连接状态指示** | 无已连接/重连中/断开 UI | 用户无法感知连接健康度 |
| **Todo 面板** | 未实现（但 serve 端已有 `GET /todos`） | 缺任务进度可视化 |
| **Patch diff 渲染** | Prism_diff 语法已内置，但无 diff 组件；ToolCard 只显示原始 args/output | 代码变更不可读 |
| **Files 页** | 无（服务端无 /file API，见第三节评估） | 缺文件浏览入口 |
| **网络安全配置** | `base-config cleartextTrafficPermitted="true"` 全局放行明文 | 过度宽松，可白名单化 |

## 二、总体架构设计

### 2.1 分层架构

```
┌──────────────────────── Android Client（Compose）────────────────────────┐
│ UI Layer                        ViewModel Layer        Data Layer        │
│  ChatScreen(Files/Settings)  →  ChatViewModel        →  ChatRepository   │
│  NavigationBar + NavHost         (StateFlow)             │               │
│  TodoPanel / DiffCard / …                              ReasonixApi(REST) │
│                                                      ReasonixSseClient   │
└────────────────────────────────────────┬─────────────────────────────────┘
                                         │ OkHttp（REST + SSE）
                                         ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Reasonix serve（esengine/DeepSeek-Reasonix main-v2，DeepSeek 协议上游）  │
│  GET /events(SSE) /history /context /status /models /sessions /skills    │
│  /todos /checkpoints /branches；POST /submit /cancel /approve /plan …     │
└──────────────────────────────────────────────────────────────────────────┘
```

- **保持现有分层**（UI → ViewModel → Repository → API/SSE），与 opencode_android_client（UI → MainViewModel → OpenCodeApi/SSEClient/Repository）结构同构，也与 openMode 的 Clean Architecture 分层思想一致——这是"设计参考不搬代码"的最大红利：**我们已有与参考项目同构的分层**。
- **新增模块**：`ui/navigation`（导航骨架 + 屏幕路由）、`ui/files`（Files 页）、`ui/components/TodoPanel.kt`、`ui/components/DiffCard.kt`、`data/api` 增加 todos 等端点方法。

### 2.2 通信层：Reasonix（DeepSeek-Reasonix）协议

**已核实的 serve 端点清单（main-v2 `internal/serve/serve.go` 逐行核对）**：

| 方法 | 端点 | 客户端现状 |
|---|---|---|
| GET | `/events`（SSE）、`/history`、`/context`、`/status`、`/models`、`/sessions` | ✅ 已实现 |
| GET | `/todos`、`/skills`、`/checkpoints`、`/branches` | ⚠️ todos 待接入；其余暂不接 |
| POST | `/submit` `/cancel` `/approve` `/plan` `/compact` `/new` `/rewind` `/fork` `/summarize` `/answer` `/resume` `/delete-session` | ✅ 已实现 |
| POST | `/tool-approval-mode`、`/auto-approve-tools`、`/bypass`、`/goal`、`/forget` | ⚠️ 部分已实现，其余按需 |
| 认证 | serve 支持 none / token / password 三种（`authGate`；`reasonix.example.toml` `[serve]` 段已核实：token 为 pre-shared token，password 为 bcrypt） | ⚠️ 客户端已支持 Basic Auth，token/password 模式需实测认证头格式 |

**SSE 事件流**（`SseEventKind` 15 种）：`turn_started / reasoning / text / message / tool_dispatch / tool_result / tool_progress / usage / notice / phase / approval_request / ask_request / compaction_started / compaction_done / turn_done` —— 客户端 `Models.kt` 已全覆盖。

**兼容性原则**：客户端 JSON 解析一律宽松（Gson 忽略未知字段、解析失败跳过），serve 端新增字段（如 `/status` 已增加 `cwd/goal/goalStatus/jobs`）不影响现有功能。

### 2.3 UI 层：Compose 导航

```
MainActivity
├─ 未配置服务器 → ServerConfigScreen（启动引导，保持现状）
└─ 已配置 → 主框架
    ├─ 手机（WindowWidthSizeClass.Compact/Medium）
    │   └─ Scaffold(bottomBar = NavigationBar) { NavHost }
    │       ├─ Chat（startDestination）
    │       ├─ Files
    │       └─ Settings（从全屏覆盖层迁入 Tab）
    └─ 平板（WindowWidthSizeClass.Expanded）→ 三栏（Sessions/Settings | Files | Chat）
```

- 借鉴 opencode_android_client `PhoneLayout`（MainActivity.kt:225-300）：`NavigationBar` + `NavigationBarItem`（selected/unselected 双图标）+ `NavHost`，顶层切换用 `popUpTo(startDestination){saveState=true} + launchSingleTop + restoreState` 保留各 Tab 状态。
- **Settings 迁移**：现有 `SettingsScreen` 是"全屏覆盖层"（`ChatUiState.showSettings` 控制），迁移为独立 Tab 后复用同一 Composable 与回调集合（`onThemeModeChange`/`onModelSelect`/`onCiSettingsChange`…），只是宿主从覆盖层变为 NavHost 页面；Chat 顶栏的设置入口改为 `navigateToTopLevel(Settings)`。
- **ChatViewModel 生命周期**：保持单例级（Activity 持有，跨 Tab 共享）还是 Tab 级？推荐**保持共享**：Chat 会话状态（消息/流式/SseCollectionJob）不应因切 Tab 而销毁；Files/Todo 各自持有独立 ViewModel。

## 五、关键技术选型

### 5.1 Markdown 渲染：Markwon 现状评估 → **保持，不换**

现状：`MarkwonRenderer` 已接入 Markwon 4.6.2 全插件集（tables/tasklist/html/图像(coil+glide)/linkify/strikethrough/inline-parser）+ Prism4j 60+ 语法（含 diff）+ `PrecomputedTextSetterCompat` 异步排版 + `NoCopySpannableFactory` 流式防闪烁 + 明暗主题色插件，经 24 个提交打磨。

对比：opencode_android_client 用 `multiplatform-markdown-renderer-m3`（Compose 原生）——他们是**从零起步**的选择；我们**已有可用且完整的 Markwon 管线**，迁移收益低、回归风险高。**结论：保留 Markwon**，后续如遇性能瓶颈再评估 `markwon-recycler`/`recycler-table` 组件化方案（依赖已声明）。

### 5.2 Patch diff：服务端无 `/diff` 端点 → **事件内解析 + Prism_diff 渲染**

- 数据来源：`tool_dispatch`/`tool_result` 的 `args`/`output` 中的 SEARCH/REPLACE 块（Reasonix `edit_file` 工具格式）与 `apply_patch` 输出
- 渲染：归一化 diff 行模型 → `Prism_diff` 语法高亮（`DefaultGrammarLocator` 已注册 `diff`）+ 自定义行着色（`+` 绿 / `-` 红 / `@@` 头）
- 升级路径：上游 `/diff` 端点合入后，数据源切换为 API，渲染组件复用
- 备选：`io.noties:markwon-recycler` 等不适用（非 diff 场景），不引入新依赖

### 5.3 文件树：服务端无 `/file` API → **轻量聚合版（P2）**

- 聚合源：会话内 `read_file`/`edit_file`/`write_file` 事件的 `subject`/`paths` 参数 → 文件路径集合 + 操作类型状态色（added/modified/deleted，借鉴 opencode `FileBrowserPane` 的 `FileNode`+status 配色思路）
- 内容：`tool_result.output` 缓存；无缓存提示"内容在服务器上"
- 完整文件树 + git 操作：**依赖上游 `/file` 系列端点**（feature request 已列入批 4）

### 5.4 网络层：OkHttp（保持）+ 补重连策略

| 项 | 现状 | 动作 |
|---|---|---|
| REST | OkHttp 同步 + Dispatchers.IO（120s 超时） | 保持 |
| SSE | OkHttp SSE `EventSources`，`onFailure → close()` | **补指数退避重连**（1s→30s，借鉴 opencode `SSEClient`）；HTTP 层错误（404/401）不重连 |
| 认证 | Basic Auth 头（可选） | 保持；对齐 serve `authGate`（none/token/password，已核实配置项），token/password 模式实测后扩展认证头 |
| 明文流量 | 全局放行 | 白名单化（localhost/10.0.2.2/*.ts.net） |

### 5.5 安全存储：CredentialCrypto（现状）**优于** EncryptedSharedPreferences

- 现有实现：AES-256-GCM，密钥存 AndroidKeyStore（不可导出），`enc:v1:` 前缀 + 明文自动迁移 + 备份排除规则（`backup_rules.xml` 已排除凭据文件）
- EncryptedSharedPreferences 同为"Keystore 主密钥 + AES-GCM 值加密"，且已标记 deprecated（androidx.security 1.1.0 起）；**结论：不引入，不迁移**。档案 P1 项"EncryptedSharedPreferences"已过时，标记为已达成（以更强方案）。

### 5.6 序列化：Gson（保持）vs Kotlinx Serialization

- 现状 Gson + TypeToken 宽松解析（未知字段忽略、失败空值）——正是**协议演进兼容**需要的
- opencode 用 Kotlinx Serialization 是其一贯技术栈；我们切换收益低（无 @Serializable 编译期收益于宽松协议场景）
- **结论：保持 Gson**

## 六、风险与注意事项

### 6.1 协议兼容风险（高关注）

| 风险 | 说明 | 对策 |
|---|---|---|
| serve 端点演进 | 上游活跃（v2 重写中），已见 `/resume`/`/compact` 修复、`/status` 增字段、新增 `/skills`/`/todos`/`/forget` | 客户端全宽松解析；SSE 事件按 kind 白名单分发，未知 kind 忽略；每批验证对当前 serve 版本 |
| 认证模式差异 | serve 支持 none/token/password（已核实 `reasonix.example.toml` `[serve]`：token=pre-shared token 可自动生成，password=bcrypt 经 `reasonix serve --hash-password`）；客户端仅实现 Basic Auth | 实测 serve 各认证模式的实际认证头（token 模式未必是 Basic 头，可能为 Bearer/自定义头）；按实测结果扩展 `ReasonixApi`/`ReasonixSseClient` 认证头逻辑；连接验证错误提示明确区分 401/403 |
| 会话并发绑定 | serve 有 session lease（`bindMu`），多运行时同开一会话会 409/refuse | 客户端重连/切换会话时对 409 提示"会话被其他终端占用" |
| 断流丢消息 | SSE 断连期间事件丢失 | 批 2 重连后 `/history` 增量合并 |

### 6.2 构建 CI 风险

- AGP 9.1.1 + JDK 17：CI 已固定 temurin 17，**本地必须同版本**（ECS 上若用其他 JDK 会编不过）
- `org.gradle.jvmargs=-Xmx2048m`：大依赖（Prism4j 60+ 文件）编译吃内存，见 6.4
- 缓存 key 含 `libs.versions.toml`：**改版本号会失效缓存**，首编变慢属正常
- 新增文件必须留在 `app/src/main/java` 下并被 git 跟踪，否则 CI 产物缺功能

### 6.3 签名与发布

- reasonix.jks 是**固定签名**：升级安装必须同签名，换机/重签会导致"覆盖安装失败、需卸载重装（丢数据）"
- secrets（KEYSTORE_BASE64/PASSWORD/KEY_ALIAS/KEY_PASSWORD）**只存在 GitHub secrets 与 ECS local.properties**；严禁提交进 git（.gitignore 已含 local.properties，需保持）
- Release 流程：workflow_dispatch → 自动建 tag（versionName）→ 上传 debug+release APK；**发布前人工确认 versionName 递增**（当前 1.0）

### 6.4 ECS 资源限制

- 构建内存：`-Xmx2048m` 对全量 `assembleDebug` 偏紧（Prism4j + Compose KGP），批验证建议 `./gradlew assembleDebug` 首次冷编预留 5-10 分钟；如 OOM → 临时加 `org.gradle.jvmargs` 或 `--no-daemon`，**不要**为此改 AGP/Kotlin 版本
- 无本地模拟器：功能验证以 CI 编译 + 真机（手机）为准；UI 走查用 Compose Preview 最小化
- 磁盘：gradle 缓存 + build 产物增长快，定期 `./gradlew clean`

### 6.5 安全注意

- Basic Auth 走明文 HTTP 时凭据可被嗅探 → 设置页提示建议 HTTPS/Tailscale（借鉴 opencode README 远程访问指引）
- `network_security_config` 收紧后需回归 HTTP 局域网直连场景（批 5 验证）
- CredentialCrypto 解密失败（换机恢复）返回 null → 调用方按空值处理已实现，勿改回明文降级

### 6.6 上游依赖风险（Files 页）

- **Reasonix serve 无 `/file` 系列与 `/diff` 端点**（已逐行核对 serve.go）；opencode server 有 → Files 页完整版**必须依赖上游新增 API**，不能在本仓库内实现（除非走 6.5 的 SSH 直连方案，属大改，不推荐）
- 对策：批 4 提交 feature request + 轻量聚合版先行；本方案与 README 明示该依赖

## 附：决策记录

1. **Files 页策略**：服务端无 `/file` API（已核实），档案 P1 修正为 **P2 轻量聚合版 + 上游 feature request**（本方案推荐方案 A，非交互环境按最安全可逆默认执行；若后续用户选择"等上游"或"SSH 直连"，仅影响批 4 范围，不影响批 1-3）。

## 结论

- 档案三大结论**成立**：opencode_android_client 是最直接参考（场景/技术栈一致、本地源码齐全、活跃维护）；"不搬代码只做设计参考"的增量策略正确（协议不兼容已核实、现有 24 提交投入明确）；优先级需 3 处修正（Files 降 P2、EncryptedSharedPreferences 已达成、diff/todo 对调）。
- 开发按 5 批推进，每批独立可编译：**批 1 底部 Tab → 批 2 SSE 重连+连接状态 → 批 3 Todo+Diff → 批 4 Files 轻量版+上游请求 → 批 5 安全收紧+收尾**。
- 最大增量价值点：底部 Tab 导航骨架（解锁 Files 入口）+ SSE 断线自愈（当前真实短板）。
